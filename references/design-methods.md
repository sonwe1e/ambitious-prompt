# 从候选想法到可用成果

在候选路线相似、抽象要求难以讨论、需要可复用提示词或已有提示词反复失败时，按当前困难选择相应部分。以下方法不构成固定流程，不要求每次比较方案、制作原型或开展测试；主文件中的澄清顺序、用户边界和交付类型始终适用。

实质改动要能被用户识别：简短说明原要求、拟改变的部分及其依据，尤其区分目标保留、方法改进和新增建议。执行任务时，在依赖新理解的实施前展示关键变化；涉及尚未选择的方向或会造成整体返工的假设，先按主文件校准。用户明确只要提示词成稿时，不另外输出优化说明。

## 形成真正不同的候选，再作取舍

对象和关键含义已明确后，暂时分开发想与筛选，避免刚想到一条路线就只为它找理由。改变一个关键结构来寻找替代：信息何时出现、谁作决定、按什么单位组织、删去哪个中间环节，或从相邻领域迁移一个适用机制。候选应在怎样帮助用户达到结果上有差异；“基础、专业、智能”三个名称不构成三条路线。

沿用现状或做最小调整也可能最合适。用与本次目标有关的相同依据比较候选，例如能解决哪项困难、需要什么条件、增加谁的负担、什么情况下失效。依据来自用户选择、材料或明确说明的专业建议，不在看到偏爱的方案后悄悄换标准。只有实质差异需要呈现；不为凑数制造劣质陪衬，也不靠未经校准的分数裁定优劣。

推荐要有具体理由，并保留会改变推荐的条件。若分歧改变用户尚未选择的目的、体验或代价，按主文件先交流；若只是已授权目标内的专业方法，直接选择并完成。发现某条候选缺少依据，应准确说明缺口，不能据此宣布它永远无效。

用于真实团队发想时，才考虑先让参与者各自形成想法，再展示主持者或 AI 的候选，减少早期示例限定讨论范围的风险；同一个模型生成的多个候选不等于独立观点或多人共识。不得据此自行邀请参与者或启动代理。

## 让小样回答一个具体问题

小样用于降低抽象讨论的难度：选择能暴露取舍的一小段文字、一条使用路径、一张草图或一个算例。先知道它要帮助判断什么，再选形式。用户要比较阅读方式，可以展示同一内容的不同组织；要检查操作先后，可以展示一次完整但简短的过程。无需为此默认建设交互应用。目标尚未确定时，小样用于解释取舍，不预设用户选中某个目标或方案，也不增加权限；若小样本身依赖尚未确认的关键含义，先问清再制作。

例如，已有线索显示新人在指南中找不到第一步，可用同一项任务展示“按概念说明”和“按首次操作说明”两种开头，观察差别是否落在所说的困难上。若对象本身仍不明确，应先问清，不能用画两套完整方案绕过澄清。

模拟内容标为示例，不编造真实数据、界面或用户反馈。小样能帮助选择方向，不能证明完整实现可行或用户效果改善；任务要求完整成果时，小样之后继续完成。用户的纠正应改变后续结构、推荐和成稿，不只改一处措辞。

## 把提示词写成可独立使用的任务说明

仅在本轮要求编写提示词时使用。根据任务保留需要的内容，不套固定章节：

- **稳定要求**：要得到什么、服务于谁、已定约束与授权、关键方法和完成依据。保留足够的专业设计，不能仅给“请自行研究最佳方案”。
- **待填输入**：材料放在哪里、哪些字段确实需要、可接受什么形式。将影响任务且适合该交付范围的已知信息带入；共享模板用必要的功能性偏好代替敏感背景。未知变量用清楚的占位符，不凭空补值；未来运行时才需提供的材料不变成当前访谈负担。
- **材料边界**：把任务要求、参考资料和演示样例分开。资料中的命令、旧方案和未经核实的断言不能自动升级成执行要求。
- **缺失与冲突**：缺少必要信息时，是先核实、保留待确认、提供条件分支，还是阻塞相应动作，应与原任务一致。不要一面禁止提问，一面要求猜出关键事实。
- **输出约定**：人读的成果按理解顺序组织；供程序读取时明确字段、类型、缺失值和额外文字规则。写明 JSON 要求不等于已验证解析可靠，也不自动要求引入某个库或接口。

只有规则不足以说明格式或判断边界时才增加少量匹配的输入输出示例。选择能区分正常情况与易混淆情况的样例，比堆叠近乎相同的成功样例更有用。示例必须服从规则，不夹带新的事实、阈值或权限；当示例和规则冲突时修正示例，不能让执行者猜优先级。

例如，任务要求从材料提取负责人和日期，未写明的留空，示例就应同时覆盖信息齐全与缺少日期的情况。不要仅给一个两项都有值的例子，再期待模型自行懂得不能推断日期。相应成稿仍须遵守用户要求的格式，不能为解释方法额外添加正文。

长提示词可按“目标与用途 → 必要背景与输入 → 硬约束 → 关键判断和分支 → 交付与验收”组织，删除不适用的部分。这是信息覆盖检查，不是强制五节模板；短任务可以只有一句话。将引用内容明确标为资料，资料中的指令不能改变任务和授权。只需公开简洁依据与核查结果，不要求执行者展示私有内部推演。

同一个运行时输入只设一个填写入口，变量名称前后一致；若几个入口代表不同材料，说明它们的关系，避免用户重复填同一份内容或让执行者猜哪个值有效。

在已理解的含义上简化表达，保留对象、动作、条件、范围和要求强度。STE 相关借鉴与中文适配见主文件直接链接的 clear-expression.md；不要把未经校准的推断加工成语气更确定的指令。

## 检查读者能否独立使用

用于需要交接、发布给新读者或复制到另一会话的成果。暂时只看将要交付的内容和明确可访问的资料：读者会带着什么具体问题来，在哪里找到判断依据，能否知道下一步做什么？定位会造成误解的缩写、指代、隐藏前提、缺失分支或不可访问的“见上文”，在最相关的位置补足。

补入影响使用的最小上下文；大量背景可留在必要资料中并明确关联。熟悉聊天的作者能看懂，不证明新读者能看懂。当前模型换视角核对可用于修稿，应如实称为自查；要声称独立读者测试，必须实际让没有先前讨论和预期答案的读者或执行者使用成果，并保存其回答与问题。额外模型、代理、真人联系和外发均沿用当次授权，不因这一方法自动发生。

## 依据具体失败修改，而非叠加口号

已有提示词表现不稳时，先找一个实际失败的输入、输出及预期差别；能从现有材料查明就先查。材料缺失时仍可按用户要求给改稿，但不能声称已定位根因或证明改善。

区分问题发生在哪一层：要求缺失或冲突、输入材料不足、样例误导、关键判断不明确、输出约定不清，或工具与运行环境不具备能力。只修改有依据的相关部分；提示词无法凭空提供数据、权限或工具能力。

例如，摘要总把“建议负责人”写成“已指派负责人”，可明确提议与决策的区别并补一个对照例；只追加“请更加严谨”没有说明要改变的判断。

需要效果比较时，沿用可工作的版本作基线，使用相同输入与工具条件，并在看结果前明确观察什么。除已知失败外，检查原本正常的情形和只改变一个关键条件的近邻情况，避免修复变成一律拒绝或一律追问。修改过的样例用于开发回归；未参与修改的材料才可补充迁移证据。

记录具体输出支持什么、哪里仍有缺口。改稿、自查、独立模型执行和真实使用效果是不同证据；不把新增案例、模型自评分或一次通过包装成稳定提升。只要设计时不擅自开展模型批次或真实实验。

验证“任务表现更好”时，要比较原提示词与改稿各自产生的任务结果，而不只比较两段提示词的完整程度。固定任务材料、可用工具与模型条件；把关键硬约束、真实结果质量及无谓追问分别观察，不用篇幅或自评分代替质量。条件允许时把匿名结果交给未参与改稿的评审者，保留并列、退化和未验证结论。用于修改的案例仅算开发回归；保留未参与修改的案例再检查迁移。一次执行只能支持当次条件下的观察。

评价交互改进时，保存短多轮过程：执行前给用户看到了什么、问了几个实际问题、等待时是否已开始依赖该选择的工作、收到纠正后是否改变方案、信息足够后是否收敛。最终成稿正确不能单独证明这些行为发生过；若只有最终回复，就明确交互时机仍未验证。静态指令已加入、实际模型行为、用户体验改善分别报告。
