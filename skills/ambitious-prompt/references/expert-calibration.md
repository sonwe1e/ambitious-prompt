# 专业判断如何变成有依据的雄心

在量化目标、解释模拟结果、判断能力边界或用户不知道专业上能做到什么时使用。目标是在设计提示词时就贡献可用判断；下面的区分服务于决策，不要求在每份输出中填一套表。

## 证据支持到哪里，行动就承诺到哪里

| 信息 | 如何使用 | 如何表达 |
| --- | --- | --- |
| 稳定的专业知识 | 解释机制、提出候选路线；不能证明本任务恰有该问题 | “这种机制可能解释……目前还需区分……” |
| 当前任务的观察或可比证据 | 支持所观察版本、负载、样本与对象范围内的结论 | “这次回放在这些条件下出现……尚不能说明……” |
| 专业推断 | 指出证据怎样支持解释，以及什么会使路线改变 | “若主要成本确实来自……优先做……；否则转向……” |
| 候选规则或体验目标 | 给用户可判断的收益与代价；接受后成为要求，不因此变成事实 | “建议采用……它改善……但可能牺牲……” |

用户提供的历史报告可以作为输入，不必一律重跑；但应写成“材料报告”，不能冒充亲自复验或当前版本状态。当前材料与旧结论冲突时，以适用范围和时序解释差异，先核实影响行动的部分。需要最新、细分或不确定的专业事实时，核查一手来源；没有检索条件时保留尚未核实的状态，并给出条件式方案。

派生量的名称也属于结论。区分“未记录”“尚未发生”“在另一事件之前发生”等不同含义，注明会影响判断的观察窗口。例如，截止时未收到的作业不能仅凭缺交记录称为“迟交作业”，后者暗示已收到。保持名称与实际计算、状态及样本范围一致，不要求为低影响字段额外展开审计。

支撑关键路线的引用应尽量直达相应章节、图表或数据。引用中附带的页码、锚点和版本也要对应实际内容；图号已核实而页码未核实时，给准确图号和文档链接即可，不为显得精确而补猜位置。

不能只把“根因”换成“可能根因”，却保留无条件更换系统的命令。让执行动作也相应变化：先取得能区分解释的证据，结果支持时采用候选方案，反证出现时改变路线。用户认可某种体验，也不能证明某项接口、算法或数据能力实际存在。

## 模拟、样本与因果判断

当结论依赖代理、模拟器或自动评估时，检查结论是否被输入选择、策略或判定方式预先决定。例如，虚构的排班模拟器只提出加班方案，而员工代理固定拒绝所有加班；“零方案被接受”证明的是这组策略不相容，不能据此认定真实员工不愿协商或必须新增某项产品功能。

先核对结果的产生机制，再决定值得比较什么。若同时改变规则、代理策略和输入，改善只能先归于这组改动；要判断某项改动的贡献，保留可比的策略与负载，或加入能区分主要解释的对照。需要模拟真实行为时说明代表性依据；策略压力测试也有价值，但不能称为真人体验验证。不要求所有任务做完整因子实验。

旧基线用于比较，不是必须永远复现某个坏数字的规格。随机观测中的“零次”“全部”不是自动成立的确定性断言。报告运行条件与差异，只有规则本身保证的不变量才适合严格断言；不要要求换一批随机条件仍精确得到旧统计量。

## 校准最重要的目标

先找会改变方案的关键条件，再看专业参照是否可迁移。推理性能常受模型、硬件、精度、输入输出长度、并发与缓存状态影响；设计作品则受使用场景、受众和媒介限制影响。用户不需要先学会这些术语，你可以解释最关键的区别并建议默认选择。

资料足够时，明确给出当前水平、可比较的参考水平、建议挑战的目标及依据。比较对象必须在关键条件上匹配，差异应披露。理论极限用于理解机会和边界，不等同于工程上必然可达的目标。

资料不足时，可以先给机制上成立的候选路径、哪些条件会使其有效，以及条件式目标。例如“如果目前主要是重复计算，我们应把复用后的成本作为目标，而不是只压低单次计算的常数”。只有决定是否成立的未知项才值得追问；不要列出二十项硬件参数表。

用户已经给出低目标时，检查该目标是否被过去的成本或经验限制。说明为什么更大的改进可能值得尝试，以及增量成本和验证方法。用户给出过高目标时，指出瓶颈和改变哪些条件才可能接近它，同时保留可检验的挑战路线。

## 数字先确定角色，再决定是否验收

| 角色 | 写入提示词的方式 |
| --- | --- |
| 用户明确要求或既有契约 | 保留来源与含义。若冲突或不可行，解释需要的取舍，不擅自降低。 |
| 有证据的进取目标 | 给出可比基线、估算或参照及适用条件；明确是待验证挑战还是已约定的验收线。 |
| 候选参数或阈值 | 写明选择依据及待验证影响。缺少依据时不编精确值；用机制与取舍提出比较方案。 |
| 诊断统计量 | 用来理解过程及定位问题；不能自动充当成功条件。 |

对会决定成败的数字，回答三个问题：为什么是这个水平，怎样测量，它支持什么决策。无须为每个低影响的默认参数研究文献；但任意默认值也不能成为质量已达标的证据。

指标可能与目标分离。例如，鼓励互动可能提高消息次数却增加打扰；增加讨论不一定改善决策。设定行为目标前说明它服务的用户结果，并保留能识别副作用的证据。多个目标还应检查逻辑：在只会“提前结束或用完固定时限”的流程中，中位完成时间短于时限，已要求约半数提前结束，不能同时把“少量提前结束”当成同等强度的目标。这是推导示例，不是推荐阈值。

缺少校准条件时，交付机制明确的目标和范围有限的比较：用哪些已有数据或代表性场景、区分哪项解释、什么结果足以选下一条路线。此时停止补证的条件是能够做出这项选择；不能扩成无限调研，也不能测完后挑一个刚好能通过的门槛。新拟定的验收线应在用于判断成功前说明依据并固定口径；用户原有要求不因此降格。无法测到核心效果时明确仍待验证。

## 数字如何有依据：一个虚构计算例

以下是教学用的合成测量，不代表任何真实模型、硬件或行业水平：一条串行、无重叠的固定回放请求耗时 1,200 ms，其中 900 ms 来自目标阶段，300 ms 来自本次不改变的其他阶段。相同输入与精度下，候选实现的独立测量把目标阶段降到 300 ms。

- 对应端到端估算是 `300 + 300 = 600 ms`，因此可提出端到端约 2 倍提速的集成挑战。
- 即使目标阶段耗时降为零，这条局部路线也只能到 300 ms，即约 4 倍提速；它不是所有可能系统改造的上限。
- 独立测量尚未证明集成结果。需要检查额外开销、正确性和不同输入上的表现，不能直接声称达到 2 倍。
- 若要继续追求更快，应检查剩余 300 ms 是否可改变，或原串行假设是否仍成立，而非机械地让同一个阶段无限提速。

这里的“雄心”是用已有证据提出完整系统的挑战，再寻找剩余空间。不要把这些数字搬入另一份提示词。

## AI inference：专业知识应该贡献什么

“更快”可能指更早看到第一个 token、后续生成更流畅，或同一台设备承接更多请求。这些目标需要不同的测量和取舍。先结合场景推荐目标，再问用户最在意的体验；不要只问“你想快多少”。

根据当前实现和证据判断应调查计算、访存、调度、重复工作或通信等因素，再选择候选方法。不要把量化、批处理、缓存、编译或更换引擎列成必做清单。质量、负载和成本约束应与性能目标同时进入提示词。

输出的任务应比较同条件的基线与候选方案，记录影响结果的配置，检查代表性输入的正确性和质量，并清楚区分单段实验与完整请求表现。只改善一个指标是否足够，应由实际使用目标决定。

用于核对概念和测量方式的一手资料：

- [vLLM Benchmark CLI](https://docs.vllm.ai/en/stable/benchmarking/cli/)：区分服务、吞吐和延迟的基准入口及相关指标。版本和命令使用前再核对。
- [NVIDIA GPU Performance Background](https://docs.nvidia.com/deeplearning/performance/dl-performance-gpu-background/index.html)：从计算、带宽与延迟理解性能限制。这是机制参考，不是特定模型的速度承诺。

## 非数值任务同样需要进取目标

论文讲解可以追求“听众能用一个新例子解释方法为何有效，并指出它在哪种条件下失效”，而不只追求覆盖章节。专题分享可以追求“听众能用共同维度比较几类方法，并判断当前论文填补了什么空缺”。

将上述水平落实为例子、对比框架、反例和理解检查。视觉设计负责让这些关系可见，语言组织负责让听众跟得上；这些要求彼此协同，而非用一个主观分数假装客观验收。
